# Charon implementation plans

Originally generated by the `improve` skill on 2026-07-30 and refined with the
`apple-design` interaction principles. The repository is now implemented
through the completed plans listed below. Execute only one remaining plan at a
time and respect its dependency column. Each executor must read its plan fully,
run every verification gate, honor every STOP condition, and update its status
row here when done.

`Charon` is the working product name. It is a local-first, keyboard-first
desktop scratchpad and prompt-idea todo list inspired by Copper, not a clone of
its branding or proprietary implementation. The repository is a Bun workspace
monorepo containing the desktop app, a static Astro preview site, and one
framework-neutral theme package.

Follow [`plans/LAUNCH.md`](./LAUNCH.md) for the current prerequisites and launch
commands for the desktop app or Astro preview.

## Monorepo architecture

```text
Charon/
  apps/
    desktop/                 # React, Vite, TanStack, Paraglide, Tauri
      src/
        motion/              # app-owned springs, preferences, press feedback
      src-tauri/
      messages/
    site/                    # Astro static product and download site
      src/
      public/
  packages/
    theme/                   # framework-neutral tokens, themes, motion contract
  scripts/                   # repo-level verification and release policy
  plans/
```

- Bun workspaces and one root `bun.lock` are the orchestration boundary.
- `@charon/theme` exports CSS variables and tiny typed theme metadata only. It
  has no React, Astro, Base UI, Tauri, Router, or chart dependency.
- `apps/desktop` owns shadcn Base UI source, Paraglide application messages, and
  all native behavior. It also owns `motion` and the React animation adapters;
  runtime animation code must never leak into `@charon/theme`.
- `apps/site` is static Astro HTML by default. It uses Astro components, the
  shared theme package, and real screenshots/video captured from the app. It
  must not import desktop feature components or create a fake UI from styled
  rectangles.
- The site has independent EN/FR marketing copy and Astro locale routes. Shared
  theme does not imply a shared translation catalog or component library.
- TypeScript 7.0.2 remains the desktop and root target. `@astrojs/check 0.9.10`
  currently declares TypeScript 5/6 only, so `apps/site` pins 6.0.3 as an
  explicit isolated compatibility exception. Remove it when Astro Check supports
  TypeScript 7 and verify that Bun resolves the intended compiler per workspace.

## Architecture challenge outcome

The architecture must have three deep domain modules and thin adapters:

1. `Workspace` owns manifest parsing, note files, schema migrations, atomic
   transactions, recovery, external-change reconciliation, and domain commands.
2. `CaptureCoordinator` owns shortcut activation, gesture intent, permission
   state, selected-text acquisition, duplicate suppression, and platform
   capability fallback. On macOS it first resolves the foreground selection
   through a bounded public Accessibility ladder, then may use ADR 0010's
   single-flight synthetic Copy transaction with a complete in-memory
   pasteboard snapshot and change-count-guarded restoration. It never uses a
   private API, automatic Paste, arbitrary input, clipboard monitoring, OCR, or
   screen capture. It returns typed actions to the application layer.
3. `ClipboardComposer` owns deterministic Markdown formatting and clipboard
   writes. React rows only dispatch named commands.

TanStack Charts remains an adapter at the edge of an `Insights` module. TanStack
types must not leak into persisted data or the core domain. The highest-value
architectural recommendation is the deep `Workspace` module because it makes
data safety testable through both real-filesystem and in-memory adapters.

The monorepo is deliberately narrow. Do not create `packages/ui`,
`packages/config`, `packages/types`, or `packages/i18n` until two real consumers
need the same stable contract. Shared visual identity is achieved through
`@charon/theme`, not cross-framework component reuse.

## Product acceptance summary

- Local files only; no account, cloud sync, analytics, telemetry, or crash
  reporting.
- English is the deterministic first-run language; French is user-selectable.
- The public Astro site ships English at `/` and French at `/fr/`, with localized
  metadata, canonical URLs, and hreflang links.
- Light, Solarized, and dark themes use semantic tokens and work at every
  state, including focus, selection, destructive actions, charts, and errors.
- Desktop movement responds on press, remains interruptible, starts from the
  current presentation value, uses spring physics for state changes, and has
  reduced-motion, reduced-transparency, and increased-contrast fallbacks.
- macOS 14+ is tier 1. Linux X11 is tier 1 for a normal global accelerator;
  Wayland uses a visible fallback. Windows is supported when CI and platform
  smoke tests are green.
- `Shift`, `Shift` is a native capability, not a regular accelerator. Ship a
  configurable fallback such as `CmdOrCtrl+Shift+Space` everywhere. Never claim
  double Shift works on a platform until an automated or documented manual
  platform test proves it.
- Unmodified double Shift silently creates one note only for non-empty selected
  text obtained from the bounded public Accessibility ladder or ADR 0010's
  disclosed source Copy fallback. Command-double-Shift and the portable
  accelerator reveal the main empty editor. Charon has no dedicated capture
  window or special Quick Note entity. Protected, unsafe, timed-out, and
  unsupported content fails closed.
- Copying is explicit. The app never silently pastes into third-party windows.
  The only permitted input injection is one platform Copy command after the
  explicit capture gesture, with bounded timeout, no clipboard monitoring, and
  restoration only when no concurrent clipboard write occurred.
- Bulk deletion is recoverable through trash and undo. Permanent deletion
  requires a separate confirmation.

## Findings considered and rejected

- SQLite as the primary store: rejected for v1 because transparent Markdown
  files are a core product promise. A manifest plus individual Markdown files
  gives portability without hiding user content.
- TanStack Query or DB: rejected for v1 because there is no remote cache or
  server reconciliation problem. The Rust Workspace snapshot and event stream
  are the source of truth.
- Recharts: rejected because TanStack Charts is now active and the user selected
  it. The integration is feature-flagged only because `0.0.0` is brand new.
- Automatic paste into ChatGPT, Claude, Cursor, or other apps: rejected for v1
  due accessibility, trust, focus, and accidental-input risks. Copy-to-clipboard
  is the reliable contract.
- A shared React UI/component package: rejected because Astro should emit static
  HTML and the desktop owns Base UI behavior. Share tokens, not runtime widgets.
- Sharing Motion or React animation helpers with Astro: rejected. The desktop
  needs an interruptible runtime; the static site needs only CSS motion tokens
  and progressive enhancement, so the runtime dependency remains desktop-only.
- A server-rendered Astro adapter, CMS, account backend, analytics, or newsletter:
  rejected for v1. Static output is faster, cheaper, and consistent with the
  local-only privacy story.
- A generic repository/service layer for every entity: rejected. It would split
  cohesive invariants across shallow abstractions. Keep one deep Workspace
  boundary and introduce adapters only where they support distinct tests or OS
  implementations.
- Full WYSIWYG Markdown editing: rejected for v1. Plain Markdown editing and a
  safe preview are sufficient for fast prompt capture and keep keyboard latency
  low.
